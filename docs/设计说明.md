# 设计说明

> 这份文档记录「为什么这么做」——包括踩过的坑。想改代码前先读一遍。

## 1. 三层结构

```
AstrBot 人格（可选）        插件注入（每轮）              模型输出
┌──────────────────┐   ┌──────────────────┐   ┌─────────────────────┐
│ <!--LUCY-SKILL-->│   │ 语音协议          │   │ 中文正文             │
│ 环境说明          │ + │ （先中文，后 <ja>）│ + │ <ja>日语逐句翻译</ja> │
│ 完整版 SKILL.md   │   │ 每轮一句格式提醒    │   └─────────────────────┘
│ 导演本            │   └──────────────────┘
└──────────────────┘
```

- **AstrBot 人格**：WebUI 可见、可切、可备份；`tools/setup_astrbot_persona.py` 写入。
- **插件注入**：检测到 `<!--LUCY-SKILL-->` 就只补语音协议；没检测到才注入完整版。
  这样既不会重复 1.5 万字，也能在「人格被人改成别的东西」时自动兜底。
- **格式提醒**：每轮往 `req.extra_user_content_parts` 追一句。原因是踩过的坑 ↓

### 坑一：会话历史把人格带跑

插件装上之前，那个 QQ 会话里已经有一问一答（助手口气：「需要处理文档、PDF、表格…」）。
即使 system prompt 末尾挂着完整人格，模型仍会顺着历史继续演助手。
实测对比（`tests/test_history_drift.py`）：

| 组 | 回复 |
|---|---|
| 只有人格 | 「你好～有什么想聊的或者需要帮忙的事情吗？」→ 没有 `<ja>` → 中文兜底 → 用户听到「中文语音」 |
| 人格 + 每轮提醒 | `[温柔]お帰りなさいませ、マスター。…` + 入戏中文 |

所以：**人格放 system prompt 末尾还不够，最近位置要有一次强提醒**。

## 2. 为什么先中文、后日语

最初的设计是「先写日语朗读稿，再写中文」。问题是两段各写各的：
日语往往只写一句摘要（还被 `max_ja_chars` 截断），于是「听到的」和「看到的」不是一回事。

改成：**正文是唯一事实来源**，日语是它的逐句翻译。再用两个确定性检查兜住：

```python
def consistent(zh, ja, lo=0.55, hi=2.6):
    ratio = len(squash(ja)) / len(squash(zh))     # 字数比
    return lo <= ratio <= hi and abs(句数(zh) - 句数(ja)) <= 1
```

不合格 → 用当前会话模型做一次中→日翻译（`_translate`，敬体、自称ルーシー、数字保留）；
翻译也失败 → **这次不出声**。宁缺，不许对不上。

## 3. 为什么 TTS 那边不能把 LoRA 写进 yaml

GPT-SoVITS 的 `tts_infer.yaml` 里 `vits_weights_path` 如果是 LoRA，
会走错加载分支，产出「时长翻倍、发音崩」的残模型。正确做法：

```yaml
custom:
  version: v5turbo
  vits_weights_path: GPT_SoVITS/pretrained_models/gsv-v5-pretrained/s2Gv5turbo.pth  # 底模
```

然后运行时切：

```
GET /set_sovits_weights?weights_path=<e8 LoRA>
GET /set_gpt_weights?weights_path=<e10 ckpt>
```

插件在 `auto_start` 时会**自己生成**上面这份只含底模的 yaml，不去捡
`GPT_SoVITS/configs/tts_infer.yaml`（那份的 custom 段通常是 v2ProPlus）。

## 4. 发送策略：为什么默认 `split`

| 模式 | 行为 | 适用 |
|---|---|---|
| `split`（默认） | 先 `event.send()` 单独发语音，再让管线发文字 | 语音发送失败不连累文字；QQ 上就是「语音一条 + 文字一条」 |
| `chain` | 消息链 = `[Record, Plain]` | 平台支持一条消息多段时更紧凑 |

## 5. 性能：为什么要热身

api_v2 起来后第一次合成要吃 CUDA kernel/JIT 的开销（实测 25 秒）。
插件在 `initialize()` 里预热（切完权重后空跑一句「ん」），把这段挪到启动时，
正式消息的合成降到 1.4–3.2 秒。

## 6. 与其它插件的关系

| 插件 | 关系 |
|---|---|
| `astrbot_plugin_GPT_SoVITS`（通用 TTS） | **建议停用**。它会把约 15% 的短回复整条换成它的语音（参考音频是别的角色），还会抢 9880。露西插件优先级 20，比它的 14 先跑，跑完链里有 `Record` 它就跳过；但别赌概率 |
| `astrbot_plugin_poke_to_llm`（戳一戳） | 兼容。它用 `yield event.request_llm()` 走标准链路 → 触发本插件的人格注入与语音；它在 `priority=100000` 包了层 `event.send` 只过滤 `Reply`，不影响我们发的 `Record` |
| AstrBot 内置 TTS | 保持关闭。`provider_tts_settings.enable=false`，否则会把文字再念一遍 |

## 7. 已知限制

1. **人格体积**：完整版约 1.6 万字/轮（≈1.2–1.6 万 token）。嫌贵可以只留 AstrBot 人格 + `persona.inject=false`，或做精简版人格。
2. **中文兜底**：模型完全不写 `<ja>` 且翻译也失败时，会用中文念正文（音色仍是露西，但发音带口音）。这是最后一道兜底，正常不会走到。
3. **QQ 官方机器人的语音权限**：`record` 能否发出取决于机器人有没有「语音消息」权限；发不出时先看日志里有没有 `合成 … [ja]`。
4. **戳一戳**：只在 `aiocqhttp`（NapCat/OneBot）上有事件，`qq_official` 收不到。
5. **音色**：权重是在韩语+日语素材上微调的 LoRA，中文发音会带口音；这正是「日语朗读稿」存在的原因。
